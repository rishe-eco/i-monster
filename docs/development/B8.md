## Built

- **`lib/record.ts`, the record's one file (house rule 4).** The pure parsers `targetOf` (a path whitelist: `/` → `landing`, `/log` → `log`, `/podcast` → `podcast`, `/log/<id>` → the id, `/log/feed.xml` → the feed; the language prefix is stripped first), `isBot`, `subscribersOf`, `aggregatorOf`, `refererDomain`; the writes `countView`, `countFeed` (the month's `max`, never a sum), `countReferrer`, `clearRecord`; and `report(db, from, to)`. Each write is one statement.
- **`lib/record-middleware.ts`,** mounted with one line in `app.ts` at B1's marker, inside the ETag middleware. It runs `next()` first and counts only a `GET` the handler answered `200`, so a conditional request that leaves as a 304 counts as the 200 it stands for. It skips any request whose `Cookie` names `__Host-imnstr_session` (the name only; the value and the session table are never read). A failure is caught and `console.error` gets the error alone.
- **`recordMonth`** in `lib/dates.ts`: `YYYY-MM`, Gregorian, Latin digits, in `SITE_TZ`.
- **`recordKeysPerMonth: 500`** in `lib/limits.ts` (a plan §6.4 addition): past that many rows for one table, month and language, a new referring domain or aggregator is dropped and existing ones count on. `report` says when a month hit it.
- **CLIs** `scripts/report.ts` (`--from YYYY-MM [--to YYYY-MM]`, `--to` defaulting to this month) and `scripts/reset-content.ts` (row counts without `--yes`; with it, `entry`, `episode` with its links, and the three record tables, in one transaction; the auth tables and `setting` kept). npm scripts `report`, `reset-content`; both in `deploy/README.md` in the `dc exec -T imnstr node --import tsx scripts/…` form, with "take a backup first".
- **Tests:** `tests/unit/record.test.ts` (the parsers, every assumed user-agent format marked a guess), `tests/integration/record.test.ts` (R1–R3 in both languages, every skip, the 304 for a page and the feed, the key cap, a dropped table, AC-46, AC-47), `tests/integration/record-cli.test.ts`, and additions to `dates` and `limits`.

**The review changed** (`d6da7f6`):
- **Link-preview fetchers are not views.** Mastodon (`http.rb … Mastodon/…`), Pleroma, Akkoma, Misskey, WhatsApp, Bluesky's Cardyb, Iframely, Embedly and vkShare name themselves without "bot", so they passed the pattern. A post shared on Mastodon is fetched once by every server that receives it, so one share read as dozens of views.
- **R3 drops local names:** a single label (`intranet`, `localhost`) or a `.local`, `.lan`, `.internal`, `.localhost` or `.home.arpa` host. The reason is the card's for IP literals: they describe a reader's own network.
- **AC-47's signed-in check enumerates the router's admin API `GET`s,** as the 401 test does, and asserts each answered 200. The lane's fixed list predated B5, so `settings`, `entries` and `entries/:id` were not read; now they are, and any later stage's read is too.
- **`app.ts`'s D-8 comment** said nothing on a public route reads a cookie; it now says the record looks for the session cookie's name.

## Decided

The lane's calls (report item 4), each accepted at review:

- **R2's count** is `(\d+)\s+(subscribers?|readers?)`, 1 to 1,000,000; `0 subscribers` counts nothing.
- **The unknown-aggregator fallback** skips `Mozilla` and `compatible`, so `Mozilla/5.0 (compatible; X; 3 subscribers)` files under X, not Mozilla.
- **The bot pattern** is the card's plus `scan`, `probe`, `libwww`, `httpclient`, `pingdom`, and the review's link-preview fetchers. `feed` is in it, so a feed reader fetching a page is a bot for R1 and R3; R2 ignores the pattern.
- **Referrer:** a trailing dot is stripped; a `Referer` over 8,192 characters is skipped; hex and decimal IPv4 spellings are caught after `URL` normalises them.
- **The cap** applies to `record_feed` and `record_referrer` only. `record_view`'s keys are whitelisted paths with a published entry's id (anything else is a 404), so a client can't grow it.
- **`/fa`** answers 308 and isn't counted; `/fa/` is.
- **`reset-content`** also counts `episode_link` rows in what it prints, though they go by cascade.
- **House rule 8:** the record tests run both languages. The pages have no server branch by colour scheme, so the response is the same in both.

**Where the plan or card was wrong** (report item 5, answered here):
1. The card's AC-46 regex (`ip|addr|agent|ua|cookie|session|visitor|user`) would flag a future column with `ua` or `ip` inside a word. It holds for today's columns; a later schema change edits the test.
2. Plan §5 B8 names `podcast` as a page; the route is B7's and answers 404 today, so it isn't counted yet. The whitelist already names it: **B7's verify checks that `/podcast` and `/fa/podcast` count.**
3. "After the ETag middleware" in the card means mounted after it, which makes ETag wrap the record; that is what makes a 304 count. Tested.
4. The plan's `report(from, to)` is `report(db, from, to)`, as everything in `lib/` takes the database.
